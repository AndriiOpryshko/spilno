# Load run of 2026-11-10 (T47, first run)

Scenarios: `tests/load/`, started with `mise run load -- -base-url http://localhost:18047`
(defaults are the PRD §6 numbers: reads 50 req/s for 5 min, p95 <= 200 ms; writes 5 req/s for 5 min,
p95 <= 500 ms; 20 filings of a 5 MB extract, p95 <= 5 s). Exit code 0, every threshold met.

## Where it was measured

- Machine: OrbStack Linux VM (aarch64, 9 CPUs, 15 GB), Linux 7.2.12-orbstack, Go 1.27.3.
- Shared dev container: other tasks and the developer's own stack ran at the same time. Load average
  was 5.00 at the start and 1.08 at the end of the run, so the numbers are not from an idle machine.
- The core API (built from this worktree) and its Postgres 18.6 (docker, throwaway) ran on the same
  machine as the load generator, so the numbers carry no network cost. The API ran on the app-role
  pool with row-level security on, as in production, with `SPILNO_DEV_SIGN_IN=true`,
  `OTEL_SDK_DISABLED=true` (no telemetry export).
- Window: 17:44:50 - 17:54:52 (+02:00). Seed: 20 associations and 200 applications with extracts in 0.6 s.

Throughput: 50.0 req/s was reached on the read path; the bar is the rate itself minus 2% for the tail
of the last second.

## Notes on the method

- Open-loop generator: requests are issued at the fixed rate whatever the latency of earlier ones.
- Refusals of a decided заявка (`identity.application_not_pending`) and a repeated state change
  (`identity.association_state_unchanged`) are expected and not errors: 972 of the 1500 writes, because
  only 180 заявок were pending and the rest of the approvals and rejections hit decided ones. They are
  still timed, but a refusal is cheaper than a decision; the p95 of the writes that really changed state
  (about 530 of them) is therefore higher than the mix p95 shown and was not measured separately.
  Approvals 61.8 ms, rejections 33.4 ms, disablings and enablings 112.6 / 93.6 ms (per operation, refusals
  included) are all far under 500 ms.
- The extract fixture is generated in memory: 5 MiB starting with `%PDF-1.4`.
- Seeded data is small (220 applications); the numbers say nothing about large tables.

## How the RED was shown

- No stack: `mise run load -- -base-url http://localhost:18999` exits non-zero, "the API ... is not healthy".
- Impossible thresholds on a live stack (`-read-p95 1us -write-p95 1us -filing-p95 1ms`) exit non-zero with
  `threshold missed: p95 6ms exceeds the limit 1µs` for each scenario.
