## Findings

Owner of every finding: Andrii Opryshko. «Read» means confirmed in the code by reading; where the effect
also depends on a library or the database it says what would confirm it at run time.

### SEC-01 — Medium — With the development sign-in shim on, any visitor signs in as anyone, the оператор included

Why Medium: off unless the variable is exactly `true`, but it is the only sign-in that works today and
nothing stops it in a deployed environment. It does not block marking the feature ready; it blocks any
deployment that people other than the developer can reach.
- Where: `services/core/cmd/api/main.go:108-115`, `services/core/internal/identity/adapters/oidc/dev.go:25-35`,
  `services/core/internal/platform/config/config.go:34`, `README.md:40` («the only sign-in for now»).
- What: `GET /identity/sign-in` hands out a valid `state` to anyone; the callback takes `code` as a verified
  address, so `code=<any address>` gives that person's session. The default link signs in as
  `SPILNO_OPERATOR_EMAIL`. Unlike `SPILNO_DEV_STORAGE` (main.go:147) the sign-in shim logs no warning, and
  `TestProductionConfigHasNoDevShim` only proves the flag is off when unset.
- Fix: refuse to start with the shim unless the listener is loopback or an explicit development marker is
  set; log a warning at start; say in the README that it voids authentication. The real provider adapter
  (known gap K1) removes the reason to turn it on.
- Due: 2026-11-24, and before any deployment.

### SEC-02 — Medium — The sign-in `state` is not bound to the browser that started the flow (login CSRF)

Why Medium: needs a lure and an inattentive victim, but ends with an attacker's address seated as голова on
a genuine signed extract. Not exploitable beyond SEC-01 while only the shim exists; it must not survive
into the real provider adapter.
- Where: `services/core/internal/identity/app/signin.go:61-98`,
  `services/core/internal/identity/adapters/http/handler.go:88-97` (no cookie is set at start).
- What: `Complete` accepts any issued, unused, unexpired `state`; the PKCE verifier and nonce are kept by the
  server under that `state`, so they travel with it. An attacker starts a sign-in, signs in at the provider
  as themselves, and sends the unvisited callback link to a голова. The голова's browser gets the attacker's
  session; a заявка filed there belongs to the attacker's account, and an approval seats the attacker's
  address (`approval.go:111`, `applicant_email` of the account). The оператор's signature check passes,
  because the extract and the КЕП are real. No test covers an unknown, reused or expired `state`, nor the
  `Secure` and `SameSite` flags of the cookie (only `HttpOnly` is asserted).
- Fix: set a short-lived `HttpOnly; Secure; SameSite=Lax` cookie at start and require it to match the
  `state` at the callback (a signed cookie can carry the verifier and nonce and closes K2 and SEC-12 too);
  show the signed-in address on the filing form; tests for the three refused states and the cookie flags.
- Due: 2026-11-24, or with the provider adapter if that comes first.

### SEC-03 — Medium — No limit on a request body: an unauthenticated upload is read whole into memory

Why Medium: availability of the single API instance (and of Postgres on the same VM, SAD §7) for anyone
without a session; no data is exposed.
- Where: `services/core/internal/platform/httpapi/problem.go:53-63` and `router.go:13-23` (no
  `http.MaxBytesReader`, no size middleware), `services/core/internal/identity/module.go:48` (validator
  before the handler), `services/core/internal/identity/adapters/http/applications.go:28-40` (the session is
  checked in the handler), `services/core/cmd/api/main.go:172-176` (only `ReadHeaderTimeout`).
- What: `POST /identity/applications` and `POST /identity/applications/{application_id}/filings` pass the
  guard untouched (no `association_id`, not an operator path); the request validator then reads the whole
  body (kin-openapi v0.151.0 `openapi3filter/validate_request.go:290`, `io.ReadAll`) before the handler asks
  for a session. The 5 MB rule is enforced only afterwards (`applications.go:89`, `domain/extract_file.go:22`).
  A few concurrent multi-gigabyte posts exhaust memory; without a read timeout a slow body also holds a
  connection open. Read; not reproduced against a running server — a 1 GB post without a cookie and a
  memory profile would confirm it.
- Fix: a body cap in `httpapi.NewRouter` (about 6 MB on the two multipart routes, 1 MB elsewhere) answering
  413; check the session for `/identity/applications...` in the guard, before the validator;
  `ReadTimeout`, `WriteTimeout`, `IdleTimeout` on the server; the same cap at the proxy.
- Due: 2026-11-24.

### SEC-04 — Medium — The API can serve as a superuser with row-level security silently off

Why Medium: it removes the control ADR-0003 chose against the top risk, by the default configuration,
without any sign; the guard and the explicit filters still stand, so nothing leaks by itself.
- Where: `services/core/internal/platform/config/config.go:27-32`, `services/core/cmd/api/main.go:89-103`.
- What: the default `DATABASE_URL` is the owner `spilno:spilno` (a superuser in compose), and
  `MIGRATIONS_DATABASE_URL` falls back to `DATABASE_URL`. A start without `mise` (or a deployment that sets
  one URL, as before this feature) serves every request as a role that bypasses every policy; `FORCE` does
  not bind a superuser or a `BYPASSRLS` role. Nothing checks the serving role at start; the role checks
  live only in tests (`app_role_test.go`, `testdb`).
- Fix: at start read `rolsuper` and `rolbypassrls` of `current_user` on the serving pool and refuse to
  serve when either is true; drop the superuser default; a test for the refusal.
- Due: 2026-11-24.

### SEC-05 — Medium — No limit on filings: any signed-in address can store extracts without bound, and the app cannot delete them

Why Medium: disk and backup exhaustion of the one database, and a flooded queue for the one оператор, by
anyone with a verified address; needs no skill; cleanup needs the database owner by hand.
- Where: `services/core/internal/identity/adapters/postgres/applications.go:32-59` and `257-318`,
  `services/core/migrations/00028_create_applications.sql:35-36` (unique only per account and code while
  pending), `services/core/migrations/00036_create_app_role.sql:27` (no `DELETE`), SAD §8 «Rate limiting: N/A».
- What: one account may file a заявка for each of 10^8 codes, each with a file of up to 5 MB, and refile
  every rejected one; rows are insert-only and kept at least 5 years. SAD §8 waives rate limiting because
  «probing is watched through `identity.access.denied`», a counter that does not exist (SEC-07).
- Fix: a cap on open applications per account (for example 3) and on filings per account per day, refused
  with a catalogue code; an alert on the size of `application_extracts`.
- Due: 2026-11-24.

### SEC-06 — Medium — Every член правління can download the голова's signed extract, against PRD §6.1 and SAD §8

Why Medium: the РНОКПП inside the КЕП certificate is the one datum the PRD rates high and says is «shown to
nobody»; the audience is small and inside the association, and the behaviour is deliberate (T32), but no
document records the decision.
- Where: `services/core/internal/identity/adapters/http/card.go:73-90`,
  `services/core/internal/identity/adapters/postgres/queries/card.sql:33-39`; asserted by
  `core/identity/card_test.go` `TestCard_ExtractDownloadsForMembersOnly` and `e2e/us09-association-card.spec.ts`.
- What: any current member of the association, including one seated years later, downloads the file that
  confirmed each голова. SAD §8 «Files» says the extract is «downloaded only by the оператор and the
  applicant»; PRD §6.1 says the certificate data is kept only inside the file and shown to nobody.
- Fix: a product owner decision, then one of: record it in PRD §6.1 and SAD §8 (members may download), or
  limit the download to the голова it confirmed and the оператор and show members the date, signer and
  sha256 only.
- Due: 2026-11-24.

### SEC-08 — Low — «Today» for a roster term is the UTC date, not Europe/Kyiv

Why Low: a window of 2-3 hours after Kyiv midnight, on the day a term ends or starts.
- Where: `services/core/internal/identity/guard.go:82`, `app/memberships.go:45`, `app/card.go:26`,
  `adapters/postgres/applications.go:99`; SAD §8 says «today Europe/Kyiv», and filing already uses Kyiv
  (`domain/filing.go`).
- What: between 00:00 and 02:00 (03:00 in summer) Kyiv time a member whose term ended yesterday is still
  served, and a голова whose term starts today is not. A запит filed and approved in that window with a term
  start of today leaves the previous голова with access until the UTC date turns, against QG-2 («0 requests
  served with the old rights after the decision»).
- Fix: one Kyiv-day helper used by the four places, and a test with a fixed clock at 00:30 Kyiv.
- Due: 2026-12-08.

### SEC-09 — Low — The оператор downloads the extract under the name the applicant chose; the content check is a one-byte prefix

Why Low: needs the оператор to run a downloaded file; the оператор is one person whose account holds the queue.
- Where: `services/core/internal/identity/domain/extract_file.go:18-29`,
  `services/core/internal/identity/adapters/http/applications.go:93`, `adapters/http/review.go:156`.
- What: a file passes when it starts with `%PDF`, with `PK\x03\x04` (any zip) or with the byte `0x30`,
  which is also the character «0». The stored name, extension included, is returned in
  `Content-Disposition`, so a script named `витяг.pdf.js` that begins with `0;` is accepted and arrives on
  the оператор's disk under that name; the runbook says to open the file from disk. The response is
  `application/octet-stream` with `nosniff`, so nothing runs in the browser. `review.go` builds the header
  with `%q` while the other two downloads use `mime.FormatMediaType`.
- Fix: name the download from the sniffed type (`extract-<filing>.pdf`, `.p7s`, `.asice`) and keep the
  original name as data only; require a DER length after `0x30`; one helper for the header.
- Due: 2026-12-08.

### SEC-11 — Low — The roster policy lets a person update or delete their own entries in other associations

Why Low: no query in the code does it (all filter by association); it weakens the second line only.
- Where: `services/core/migrations/00045_enable_rls_governance.sql:29-32`,
  `services/core/migrations/00036_create_app_role.sql:23-28` (`UPDATE`, `DELETE` kept on `board_member_revisions`).
- What: the clause «or the entry carries the actor's address» sits in `USING` of a policy for all commands,
  so with association A set it also admits `DELETE` of the actor's entries in B, and an `UPDATE` that moves
  them into A (`WITH CHECK` constrains only the new row). `TestRLS_RevisionsShowTheActorsOwnEntriesInOtherAssociations`
  checks `INSERT` only. Read from the policy and the grants; not executed — a `DELETE` in that test would
  confirm it.
- Fix: a `FOR SELECT` policy with the address clause and a second policy for writes with the association
  only; or revoke `UPDATE, DELETE` on the table, which is append-only in practice.
- Due: 2026-12-08.

## Checked and found sound

- Session: 32 random bytes, only its sha256 stored; cookie `HttpOnly; Secure; SameSite=Lax; Path=/`;
  sign-out deletes the row; a refused callback answers one 401 that does not say why.
- Guard: session, then roster inside `db.InAssociation`, then the state; a non-member, an unknown id and a
  malformed id get byte-equal 403 bodies; the operator flag is asked on `/identity/operator/` only and
  never on an association path.
- Own filing: approve and reject compare the applicant account read under `FOR UPDATE` with the session
  account; a refile needs a new check; a decided application is refused; two racing approvals of competing
  заявки create one association.
- Row-level security: every table with `association_id` has a forced policy except `applications` and
  `application_decisions` (ADR-0003); the governance and finance adapters reach the database only through
  `db.From`; identity touches the pool directly only for tables without a policy.
- Downloads: the applicant's by account, the оператор's behind the operator guard, the card's by
  association and approved decision; all three are `attachment`, `application/octet-stream`, `nosniff`.
- Logs and telemetry: the app logs start and stop only; spans carry the path without the query, SQL text
  without parameters; no address, token, cookie, reason or file content is logged.
- Web: no token or personal data in web storage (only the association id of a consent in `sessionStorage`);
  no raw HTML rendering; the e2e specs and fixtures use `example.test` addresses only.

  recognised. Accepted by the product owner (Andrii Opryshko): SAD §11, ADR-0009 (clarify-prd 2026-11-10).
- A2. A personal storage account whose address is on no roster is not detectable; the оператор sees the

- K1. No adapter for the real sign-in provider; without the shim the four sign-in operations answer 501.
  `tasks/tracker.md` «Known gaps», decided 2026-11-10 (the tracker names no person; the task owner is

- K2. Sign-in state lives in process memory, enough for one API instance. `tasks/tracker.md` «Known gaps»;
